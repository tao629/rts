# 流程步骤

严格按`先规划，后设计`进行，规划阶段输出的 `intent.md` 未确认前不进入下一步；`spec.md` 定稿后再写 `plan.md`

## 规划：输出intent.md

1. 提出人用自己的话简要描述要实现的功能，想解决的问题；追问涉及的范围、用户、限制条件以及成功的标准。
2. 按照下方intent.md模板撰写结果报告，报告内容应涵盖问题、预期结果、受影响的用户和系统、限制条件以及未决问题，最后由提出人审阅无问题后定稿（状态：draft）
3. 审定后置为 accepted，进入；不做则置 closed 并留一句原因

### intent.md模板

```markdown
# 意图（Intent）: 简要描述要实现的功能或待解决的问题

Author: <姓名/角色>. 状态：<draft|finalize|discard|finish>

## 问题（Problem）

<功能/需求要解决的问题，影响范围>

## 预期结果（Proposed outcome）

<完成的标识，需详尽说明，能度量最好>

## 受影响的模块（Affected modules）

<功能/需求实现涉及的模块、文件、数据库表等>

## 约束条件（Constraints）

<安全、合规、性能、兼容性；明确不做什么>

## 未解决的问题（Open questions）

<需进一步决策、拍板的事项>
```

## 设计：输出 spec.md、plan.md

研读 intent.md 制定需求功能说明书 `spec.md`，标明与现有约束的冲突之处，最后由发起人评审，通过后再定制开发计划 `plan.md`

### spec.md

- 涉及表或表结构的调整(增、删、改)时遵守以下规约

1. 这里**不输出DDL**,只写"允许的操作集合"和"怎么算做对了"
2. 列出变更清单(封闭清单 / Closed Allowlist)
   规则:没有 CHGID 就没有 schema 变更。 实现过程中若判断还需要额外的结构变更(加列、改类型、加索引、加约束、重命名),必须回到本 spec 新增 CHGID 并重新评审,不得在实现阶段自行添加。 本清单之外的一切 schema 变更均视为违规实现。

| CHGID   | 表        | 语义变更                                                | 回滚方式          |
| ------- | --------- | ------------------------------------------------------- | ----------------- |
| CHG-001 | {{table}} | 新增 `{{col}}`,类型 {{type}},可空,无默认值,用途 {{...}} | `DROP COLUMN`     |
| CHG-002 | {{table}} | 存量 `{{col}}` 回填,来源 {{...}},预计 {{N}} 行          | 幂等重跑          |
| CHG-003 | {{table}} | 删除旧列 `{{col}}`                                      | 不可逆,仅备份恢复 |

**字段填写要求:**

- 「语义变更」列写**业务语义**:字段名、类型、是否可空、唯一性、取值域、谁写入、谁读取、存量数据从哪来。

### plan.md

用户评审确认后输出功能开发计划`plan.md`.
涉及数据库操作要优先输出 `schema.sql` 文件
