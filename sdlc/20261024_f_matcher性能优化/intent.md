# 意图（Intent）: f_matcher 在超大文件量场景下的性能优化重构

Author: zhtao. 状态：Finalize |

## 问题（Problem）

`toolkit/f_matcher` 用于在指定目录下批量扫描命中敏感关键字的 `.txt` / `.csv` 文件。当待扫描目录的文件数量很大时（审计导出的批次数据动辄几万到几十万文件），运行耗时随文件数线性增长且**单线程跑满一个核**，运维同学反馈"扫一批要等太久"，不敢在高峰期跑全量扫描。

已定位的三个成因（基线实测见下）：

1. **每个文件被完整读取两次**：先 `is_valid_utf8()` 全量读一遍做编码校验，再 `scan_utf8()` / `scan_gb18030()` 全量读一遍做匹配，I/O 与解码开销直接翻倍。
2. **关键字匹配是逐关键字重复扫描**：25 个关键字各自对整行做一次 `match_indices`，即每行文本被扫 25 遍。实测 20k 文件 / 79MB 数据集上，1 个关键字耗时 0.46s、25 个关键字耗时 2.26s——**约 80% 的耗时来自这 24 遍多余的重复扫描**。
3. **全程单线程**：扫描与目录遍历都是串行循环，多核机器上其余核心完全空闲。

另外发现 GB18030 解码路径每行都 `pending.drain(..).collect()` 分配一个新 `String`，行数多时是二次方级别的浪费。

## 预期结果（Proposed outcome）

**可度量的完成标识：**

1. **性能基线可复现**：固定数据集（2 万个 `.txt`/`.csv` 文件、约 79MB 文本、命中率 1%）下，记录优化前后的耗时与加速比，结论写入 `README.md` 的性能章节。

   | 指标 | 优化前（实测） | 优化目标 |
   |------|---------------|---------|
   | 20k 文件 / 79MB 端到端耗时 | **2.26s** | **≤ 0.30s**（≥ 7 倍加速） |
   | CPU 占用 | 100%（单核） | 多核并行 |
   | 每文件读取次数 | 2 次 | **1 次**（UTF-8 文件） |
   | 每行关键字扫描遍数 | 25 遍 | **1 遍** |

2. **并行化**：扫描与目录遍历均为多线程并行；默认按可用 CPU 核数自动决定并发度；新增 `--jobs N` 显式指定并发度（`--jobs 1` 退回串行，结果与并行时一致）。

3. **输出确定性**：无论并发度多少，stdout 的命中清单**按路径字典序**稳定输出，stderr 的告警也按路径排序——保证同一输入多次运行、单机与多机结果完全一致，可直接用于差异比对。

4. **行为等价**：优化后对同一数据集的命中文件集合、命中行号、退出码与优化前**完全一致**（用基准前后输出 diff 验证）。

5. **规则语义不变**：关键字/排除词仍从 `sensitive_rule.txt` 解析；排除语义仍是"关键字后严格紧跟排除词则不算命中"；编码识别仍是"UTF-8 优先、失败回退 GB18030"；命中即停（每文件最多一条结果）等既有语义一条不动。

6. `cargo build` / `cargo test` 通过；现有单元测试全部保留且通过；新增针对并发一致性与性能不退化的测试。

**验证方式（本地可自测）：**

- **正确性**：固定数据集跑优化前后二进制，stdout / stderr / 退出码 diff 必须为空。
- **性能**：同一数据集重复 3 次取中位数，记录 `time` 输出。
- **并发一致性**：`--jobs 1` 与 `--jobs 20` 的输出 diff 必须为空。
- **单元测试**：补充"排除词紧邻""多关键字同行""GB18030 文件"等边界的回归用例，确保重构后语义未漂移。

## 受影响的模块（Affected modules）

| 模块 | 路径 | 变更性质 |
|----|----|----|
| 敏感文件匹配工具 | `toolkit/f_matcher` | 主要改动：重构扫描与匹配内核，引入并行化与依赖 |
| 工作区清单 | `Cargo.toml`（`toolkit/f_matcher/Cargo.toml`） | 新增第三方依赖 `aho-corasick`（多关键字单遍匹配）、`rayon`（并行调度） |

不涉及 `rts-center` / `rts-core` / `r_connector` / `web-ui`，不涉及数据库，不改变对外 CLI 的既有参数语义（仅**新增** `--jobs`，不改已有参数行为）。

## 约束条件（Constraints）

**功能与兼容性约束**

- **输出格式与退出码不变**：stdout 仍为 `<绝对路径>:<行号>` 每行一条；退出码 0/1/2/3 语义不变（2 仍优先于 3）。
- **不回显敏感内容**：仍然只输出路径与行号，不输出命中行原文与命中关键字。
- **规则文件不硬编码**：关键字与排除词仍来自规则文件，支持用户自定义词表。
- **命中即停**：某文件命中 1 个关键字即终止该文件后续匹配，每文件最多一条结果。

**安全与合规约束**

- 并行化不得引入"把文件内容打印出来"的旁路——日志与告警中只允许出现路径与错误原因。
- 多线程共享的规则对象必须只读，不得在扫描过程中改写规则。
- 告警信息中不得回显文件内容片段。

**技术约束**

- 并发度必须可收敛到 1，且 `--jobs 1` 的行为与优化前完全一致（便于线上出问题时退回串行定位）。
- 内存占用不得随文件总数线性膨胀到不可控水平；单文件解码缓冲需有上限。
- 不引入会显著增加二进制体积或编译时间的依赖（不使用正则引擎、不使用 SIMD 专用库）。

**明确不做**

- 不做正则/模糊匹配、不做 UTF-16 支持、不做 GUI、不做多目录批量扫描、不与 `rts-center` 集成。
- 不做增量扫描 / 结果缓存（每次运行都全量重扫，保持"结果永远反映当前磁盘状态"的语义）。
- 不改变文件扫描范围（仍只处理 `.txt` / `.csv`）。

- **依赖引入**：允许引入 `aho-corasick` + `rayon`。**已拍板**。
- **目录遍历是否并行化**：walk 一并并行化。**已拍板**。
- 待实现阶段确认：GB18030 文件的编码判定仍需"整文件 UTF-8 合法性"语义还是可改为"前 N 字节采样"？——倾向**保留整文件语义**（不改变既有判定结果），代价是 GB18030 文件需在检测到首个非法字节后重新解码一次。
