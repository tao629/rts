# 构建计划（Plan）: f_matcher 在超大文件量场景下的性能优化重构

依据：`intent.md` + `spec.md`。状态：Finalize（已实施并验证） |

## 1. 改造总览

现有数据流：

```text
collect_files(串行 walk)
  → for file in files (串行)
      → read_head(3B)
      → is_valid_utf8(全量读第 1 次)
      → scan_utf8 / scan_gb18030(全量读第 2 次 + 逐行 × 25 遍关键字扫描)
```

目标数据流：

```text
collect_files(并行 walk, 按层 BFS)
  → rayon 并行 for file in files
      → read_head(3B)
      → 单遍流式读取：一边校验 UTF-8 一边逐行匹配(aho-corasick 单遍)
          ├─ 整文件合法 UTF-8 → 直接采用已得结果（只读 1 次）
          └─ 发现非法字节 → 回退：重开文件按 GB18030 完整解码再匹配
  → 命中结果按路径排序 → 有序输出
```

## 3. 关键实现要点

### 3.1 rule.rs：单遍多模式匹配

- 用 `aho_corasick::AhoCorasick` 一次性构建 25 个关键字的匹配器；`Rule` 持有它，`Rule` 天然 `Send + Sync`（构造后只读）。
- 逐行匹配时遍历匹配器返回的候选匹配：
  - **同关键字非重叠归一**：维护每个关键字上一次命中的结束位置，丢弃起始位置早于该结束位置的候选 → 与 `str::match_indices` 语义等价。
  - **排除判定**：命中结束位置之后的文本若以任一排除词开头 → 该候选不计命中。
  - 取**起始位置最靠前**的有效命中（保持 `find_hit` 契约）。
- 扫描器走短路路径 `is_hit()`：一旦发现有效命中即返回，不再继续找最小位置（输出只需要"有没有"）。

### 3.2 scanner.rs：单遍流式读取

- 保留 `read_head` 的 UTF-16 BOM 检查。
- UTF-8 路径：按行读取（`BufRead::read_until`），每行用 `str::from_utf8` 判定（`0x0A` 不可能是 UTF-8 多字节序列的组成字节，故逐行判定 ≡ 整文件判定）。
- 命中后**继续读完整个文件**以确认整体合法（这是"整文件 UTF-8 合法性"语义的要求）；若中途发现非法字节 → **丢弃已得命中**，回退到 GB18030 路径重扫。
- 代价：UTF-8 文件读 1 次（现状 2 次）；GB18030 文件读到首个非法字节后重扫 1 次。

### 3.3 scanner.rs：GB18030 路径

- 解码进可复用的 `Vec<u8>` 缓冲，用换行扫描切行，**每行不分配新 `String`**（现状每行 `drain().collect()` 一次分配）。
- 行号计数与 CRLF 处理保持与 UTF-8 路径一致。

### 3.4 scanner.rs：并行遍历

- 按目录**层级 BFS**：一层内的目录用 rayon 并行读取，收集子目录与文件，下一层继续。
- 语义保持：不跟随目录符号链接、只收 `.txt`/`.csv`、规则文件排除。
- 遍历顺序不定 → 最终按路径排序，保证确定性。

### 3.5 main.rs：并行扫描与有序输出

- `--jobs n`：n=1 走串行循环（退路）；n>1 构建 `rayon::ThreadPoolBuilder::num_threads(n)` 的线程池并在 `install` 内执行。
- 命中结果收集为 `(PathBuf, usize)`，**按路径排序**后输出；告警收集后按路径排序输出到 stderr。
- 退出码优先级不变：2（不完整）> 3（命中）> 0。

## 5. 风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| 重叠匹配语义漂移（§3.7） | 误报/漏报 | 按关键字做非重叠归一；用 `match_indices` 旧实现写一个对照测试随机比对 |
| 编码回退路径行号错位 | 行号报错 | 回退时从第 1 行重新计数；补 GB18030 + CRLF + 无尾换行组合用例 |
| 并行导致输出顺序不稳定 | 结果不可比对 | 结果与告警统一排序后输出；加 `--jobs 1` vs `--jobs N` 一致性测试 |
| 大文件占用内存 | OOM | 保持流式读取，不整文件读入内存；解码缓冲复用不增长 |
| 新依赖引入编译/体积负担 | 发布产物体积变大 | 仅加 2 个纯 Rust 依赖；发布后对比产物体积 |
| `rayon` 线程数与 `--jobs` 交互困惑 | 误用 | `--jobs 1` 显式串行；文档与 `--help` 写清默认值来源 |

## 7. 实施结果（实测）

### 7.1 性能

测试机：20 核（i7-12700H）/ 7GB 内存，release 构建，数据集为随机生成的 `.txt`/`.csv`，
每文件 60 行中文文本，命中率 1%。

| 场景 | 优化前 | 优化后（默认并发） | 优化后（`--jobs 1`） | 达成 |
|------|--------|--------------------|---------------------|------|
| 2 万文件 / 79MB | 2.25s | **0.07s**（约 32 倍） | 0.39s | P1（≤0.30s）✅ |
| 20 万文件 | 1.67s | **0.20s**（约 8 倍） | 0.99s | — |

- CPU 占用由 100%（单核）提升到 1250%+（多核并行）。
- 峰值内存：2 万文件 10MB、20 万文件 39MB（随文件路径列表线性增长，非内容）。
- P2/P3 由实现方式保证：UTF-8 文件只读一次；每行文本只做一遍多模式扫描。
- P4 由 1250%+ 的 CPU 占用佐证；P5 由上面的峰值内存佐证。

| 验证项 | 方法 | 结论 |
