# 意图（Intent）: r_connector 基于配置文件连接远端主机并批量执行指令

Author: zhtao. 状态：Finalize |

## 问题（Problem）

`toolkit/r_connector` 目前只有一个 `Hello, world!` 占位程序，没有任何远程连接能力。

运维同学排查远端主机问题时，需要人工开终端逐条敲 `ssh` 命令，并把命令序列记在个人终端历史里。这带来三个问题：

1. **操作入口分散**：不同人用不同工具（Xshell、putty、ssh 命令行），登录方式、端口、超时等行为没有统一约束。
2. **排查过程无法复用**：命令序列散落在各人的终端历史里，既不能作为工具能力沉淀，也没法在平台上被其它模块（如 rts-center 的任务调度）调用。
3. **凭据处理随意**：密码明文写在命令行/脚本里，容易进入 shell 历史或进程列表。

需要提供一个统一的命令行工具：**通过命令行参数传入一个配置文件**，工具按行解析出协议、连接信息、账号密码与待执行指令，建立到远端主机的连接，顺序执行配置中的指令，并把每条指令的执行结果回显到本地终端，执行完即退出。

## 预期结果（Proposed outcome）

**可度量的完成标识：**

1. `cargo build` 通过，`r_connector` 可执行文件可正常启动。
2. 命令行接受配置文件路径作为参数：`r_connector <config-file>`；文件不存在、不可读、行数不足等错误均有明确提示且退出码非零。
3. 配置文件按行解析，格式如下：

   ```text
   sftp
   192.168.1.10:2222
   root,Passw0rd
   uname -a
   ls -l /var/log
   ```

   - 第 1 行：协议，取值 `sftp` / `ssh`（大小写不敏感）。
   - 第 2 行：连接信息，`host:port` 单行形式；端口可省略，缺省 22。
   - 第 3 行：账号密码，`user,password` 逗号分隔形式。
   - 第 4 行起：待执行的指令，每行一条，按顺序执行。

   解析容错：每行去掉首尾空白；允许可选的 `标签:` 前缀（如 `连接: 192.168.1.10:22`）被剥除；空行与 `#` 开头���注释行忽略。
4. 连接建立成功/失败均有明确提示。失败时给出可诊断的错误原因（认证失败、网络不可达、主机密钥不匹配、协议不支持等），不 panic。
5. 账号行中的密码允许留空：留空时工具在本地交互式提示输入密码（不回显、不写日志），避免密码明文落盘。
6. 主机密钥策略为**首次信任并记录指纹**：首次连接打印主机密钥指纹并记录到本地 `~/.ssh/known_hosts` 文件；后续连接严格比对，指纹不匹配则拒绝连接并报错。
7. 连接成功后按配置顺序逐条执行指令，每条指令回显：指令回显、远端标准输出、标准错误、退出码；单条指令失败（退出码非零）不中断后续指令执行。
8. 全部指令执行完毕后断开连接并以退出码 0 退出（脚本化/批处理语义）。

**验证方式（本地可自测）：**

- 单元测试覆盖配置文件解析（正常、缺行、格式错误、注释/空行、端口缺省、标签前缀剥除）与默认值逻辑，无需真实远端主机。
- 手工验证：使用本地 `sshd`（或容器内 openssh-server）作为远端，跑通"读配置 → 连上 → 依次执行 `echo`/`ls`/`uname -a` → 看到回显与退出码 → 退出"的完整链路。

**命令行接口：**

```text
r_connector <config-file>        # 必填：配置文件路径
r_connector --help               # 打印用法说明（含配置格式示例）
```

## 受影响的模块（Affected modules）

| 模块 | 路径 | 变更性质 |
|----|----|----|
| 远程连接工具 | `toolkit/r_connector` | 主要改动：新增配置解析、SSH 连接、指令执行与结果回显能力 |
| 公共包 | `base/rts-core` | 仅复用（logger）；如需新增通用类型则小幅扩展 |
| 工作区清单 | `Cargo.toml` | 新增第三方依赖（纯 Rust SSH 客户端库） |

不涉及数据库、不涉及 rts-center 的接口改动。

## 约束条件（Constraints）

**安全约束**

- 密码、known_hosts 指纹以外的内容不写入日志；**密码绝不落日志、绝不回显到终端**。
- 主机密钥校验必须显式实现（首次信任并记录），不得静默跳过校验。
- 远端命令按原样透传执行（不做本地 shell 转义），但需在文档/帮助信息中明确"执行的是远端 shell 语义"。

**技术约束**

- 优先纯 Rust 实现，不引入需要本地编译的 C 库依赖（如 libssh2），避免目标机环境准备成本。
- 遵循仓库既有规约：所有开发在独立 worktree 中进行，完成本地验证后提交分支并提 PR；主仓仅用于只读查看与拉取。
- 遵循 `立项 → 开发 → 验证 → 交付 → 发布` 流程，产出物落在 `sdlc/20261023_sftp远程连接/`。

**明确不做（本次范围外）**

- 不做文件上传/下载的完整 SFTP 客户端（本次只做"连接 + 执行指令"）。
- 不做图形界面。
- 不做多主机并发/批量执行。
- 不做远程命令的本地管道串联、脚本编排。
- 不做交互式 REPL（连上后继续手工输命令）——本次为"执行完配置文件即退出"。
- 不做私钥/证书鉴权（本次仅密码鉴权）。
- 不改动 rts-center 与远程连接的集成方式（本次只交付独立命令行工具）。

## 已解决的问题（Resolved questions）

1. **底层库选型**：采用纯 Rust 的 `russh`（自带 SFTP 子系统支持，无 C 依赖），不引入需要本地编译的 `libssh2`。
2. **协议行取 `sftp` 时的语义**（已确认）：两种协议取值都走 SSH 传输层，指令统一通过 SSH `exec` 通道执行；`sftp` 仅作为配置标识保留，后续如需传文件，可在同一连接上开 SFTP 子系统。
3. **known_hosts 文件位置**（已确认）：落在用户 home 下的 `~/.ssh/known_hosts`，与 OpenSSH 工具链共用同一份信任记录。
4. **配置文件中密码的替代方案**（已确认）：密码留空时，工具在本地交互式提示输入（不回显），降低明文落盘风险。

## 仍需在 spec/plan 阶段细化的事项

- `russh` 具体 API 版本与 feature 组合、连接/认证超时的默认值取值。
- 每条指令回显的具体格式（指令回显 + stdout/stderr 边界 + 退出码的排版）。
- 单条指令失败是否影响整体退出码（默认：全部执行完仍以 0 退出，失败明细体现在回显中）。
