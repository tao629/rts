# 意图（Intent）: f_matcher 批量扫描目录下命中敏感关键字的文件

Author: zhtao. 状态：Finalize |

## 问题（Problem）

`toolkit/f_matcher` 目前只有一个 `Hello, world!` 占位程序，没有任何功能。

排查"某个目录里哪些文件含有敏感词"这类问题时，目前只能手工敲 `grep -n "部队" ...` 逐个关键字试：关键字有 24 个（且存在"关键字后紧跟某些词则不算命中"的排除规则），逐个试既慢又容易漏、也容易把该排除的误报进来。目录往往还包含多层子目录，手工 `grep -r` 难以保证只覆盖 `.txt` / `.csv`、也不便于把结果沉淀成可复核的清单。

需要一个统一的命令行工具：**传入一个目录**，工具递归遍历其下所有 `.txt` / `.csv` 文件，按 `toolkit/f_matcher/sensitive_rule.txt` 中定义的关键字规则逐行匹配；一旦某文件命中 1 个关键字即终止该文件的继续匹配；最终输出命中文件的绝对路径与命中的行号。

## 预期结果（Proposed outcome）

**可度量的完成标识：**

1. `cargo build` 通过，`f_matcher` 可执行文件可正常启动；`cargo test` 全绿。
2. 命令行接口：

   ```text
   f_matcher <dir> [--rule <rule-file>]   # 必填：待扫描目录；可选：关键字规则文件
   f_matcher --help                        # 打印用法与规则说明后退出 0
   f_matcher --version                     # 打印版本后退出 0
   ```

   - 目录不存在/不可读、规则文件不可读、参数非法 → stderr 给出明确原因，退出码非零，不 panic。
3. 目录遍历：**递归**遍历 `<dir>` 下所有层级，仅处理扩展名为 `.txt` / `.csv` 的文件（大小写不敏感，如 `A.CSV` 也算）；其它扩展名一律跳过。
4. 关键字与排除词**从 `sensitive_rule.txt` 解析**，不硬编码在代码里：
   - 关键字：规则文件中 `关键字:` 一行给出的词表（当前 24 个）。
   - 排除词：规则文件中以引号标注的排除项（当前 8 个：路、医院、宾馆、学院、家属区、宿舍、干休所、疗养院）。
   - 排除语义按"**严格紧邻**"判定：关键字后面**紧接**的字符正好是排除词时，该次匹配不计为命中（例："解放军医院"不命中；"解放军总医院"仍算命中）。
5. 匹配行为：逐行匹配，**某文件一旦命中 1 个关键字即终止该文件的继续匹配**（不再看该文件后续行），该文件只输出一次结果。
6. 输出：每个命中文件输出一行 `<绝对路径>:<行号>`，写到 stdout。例如：

   ```text
   /data/export/2026/批次1.csv:128
   ```

   - 路径为**绝对路径**；行号为该文件内命中的**行号**（从 1 开始）。
   - 输出**只含路径与行号**，不回显命中行原文与关键字（避免敏感内容二次扩散，且便于机器消费）。
7. 编码：待扫描文件按 **UTF-8 优先、失败回退 GB18030**（兼容 GBK/GB2312）自动识别解码，保证中文关键字在两种编码下都能匹配上。
8. 退出码：0 = 扫描完成且无命中；3 = 扫描完成且至少命中一个文件；1 = 参数/目录/规则文件错误；2 = 扫描过程中的致命 IO 错误。命中与否可通过退出码与 stdout 内容同时判定。

**验证方式（本地可自测）：**

- 单元测试覆盖规则文件解析（关键字行、排除词提取、多种分隔符/引号）、匹配逻辑（命中、紧邻排除、排除词不紧邻时仍命中、多关键字）、编码识别（UTF-8 / GBK）与目录遍历（只收 txt/csv、递归子目录、跳过其它扩展名）。
- 手工验证：构造含 UTF-8 与 GBK 两种编码、含命中/不命中/紧邻排除用例的临时目录树，跑通"扫目录 → 输出路径:行号 → 退出码"完整链路。

## 受影响的模块（Affected modules）

| 模块 | 路径 | 变更性质 |
|----|----|----|
| 敏感文件匹配工具 | `toolkit/f_matcher` | 主要改动：新增规则解析、目录遍历、编码识别、关键字匹配与结果输出 |
| 工作区清单 | `Cargo.toml` | 新增 workspace 成员 `toolkit/f_matcher`；新增第三方依赖 `encoding_rs`（纯 Rust 编码库，无 C 依赖） |

不涉及数据库、不涉及 `rts-center` 接口改动、不涉及 `rts-core`。

## 约束条件（Constraints）

**安全与合规约束**

- 扫描**只读**：不修改、不移动、不删除被扫描的任何文件。
- 输出**不含命中行的原文**，只输出路径与行号，降低敏感内容在终端/日志中的二次扩散。
- 关键字与排除词来自规则文件，规则文件本身不视为待扫描目标（避免规则里的关键字把规则文件本身报成命中）。

**技术约束**

- 遵循仓库既有规约：严格走 `立项 → 开发 → 验证 → 交付 → 发布` 流程，产出物落在 `sdlc/20261023_敏感文件关键字匹配/`；所有开发在独立 worktree（`.claude/worktrees/f-matcher/`）中进行，完成本地验证后提交分支并提 PR；主仓只用于拉取与只读查看。
- 目录遍历不跟随**目录**符号链接（避免环路）；文件符号链接按其目标内容扫描。
- 不引入需要本地编译 C 库的依赖；优先纯 Rust 实现。

**明确不做（本次范围外）**

- 不做正则表达式、模糊匹配、同义词扩展——严格按规则文件里的字面关键字匹配。
- 不输出命中行内容、不输出命中关键字、不生成命中统计报表。
- 不支持 UTF-16 编码的文件（检出 UTF-16 BOM 时给出告警并跳过）。
- 不做 GUI、不做多目录批量扫描、不做与 rts-center 的集成。
- 不做"关键字全量命中统计"（一次只报首个命中即停）。

## 已解决的问题（Resolved questions）

1. **文件编码策略**（已确认）：UTF-8 优先、失败回退 GB18030（兼容 GBK/GB2312），引入 `encoding_rs`。
2. **排除词语义**（已确认）：严格紧邻——关键字后紧接的字符正好是排除词才算排除；"解放军总医院"这类中间有修饰字的情况仍算命中。
3. **输出形式**（已确认）：stdout 每行 `<绝对路径>:<行号>`，不回显行内容；不额外生成报告文件。

## 仍需在 spec/plan 阶段细化的事项

- 规则文件解析的具体容错边界（标签前缀、分隔符全角/半角、引号形式）。
- 编码识别失败（既非 UTF-8 也非合法 GB18030）时的处置与告警文案。
- 目录遍历的顺序（是否需要稳定排序以保证输出可复现）。
- 退出码取值集合与是否需要区分"部分文件读取失败"。
