# 意图（Intent）: 登录环节引入图形验证码，阻断暴力破解与撞库攻击

Author: 平台研发（Claude Code 代拟）| 状态：Final | 日期：2026-10-25

## 问题（Problem）

RTS 搬运工的 Web 控制台登录页目前只有「用户名 + 密码」两个凭据，登录请求由前端打到 `server/rts-center` 的认证接口。
`server/rts-center` 目前还是空脚手架，尚无认证能力，一旦真实接口对外开放：

- 攻击者可以用脚本无限次重放登录请求，批量试口令（暴力破解 / 撞库），服务端无法区分「人」与「机器」；
- 单靠 IP 限流容易被代理池绕过，缺少与登录强绑定的、一次性的挑战因子；
- 前端只有 mock 模式（`VITE_API_MODE=mock`），前端内置演示口令即可直接登录，属于纯演示链路。

本需求要在登录链路中补上服务端生成的图形验证码：由 `server/rts-center` 生成验证码图片并维护其状态，登录时必须携带并通过校验，使自动化脚本无法在不识别图片的前提下穷举口令。

## 预期结果（Proposed outcome）

可度量的完成标准：

1. **验证码由服务端生成**：`server/rts-center` 提供验证码接口，产出验证码 ID、图片、过期时间；验证码图片不依赖第三方验证码服务与图像库。
2. **强制校验**：登录请求必须携带验证码 ID 与验证码内容；服务端**先校验验证码、后核对账号口令**。验证码缺失、错误、过期、已使用，一律拒绝登录并返回明确错误码 `INVALID_CAPTCHA`。
3. **一次性 + 有效期**：验证码校验一次即失效（无论成功失败），有效期 5 分钟；过期或重复使用的旧验证码不可通过。
4. **前端接入**：登录页展示验证码图片与输入框，图片可点击刷新；提交失败后自动刷新验证码并清空输入；mock 模式行为与真实模式一致，可本地演示。
5. **端到端可跑通**：`VITE_API_MODE=real` 时，从 rts-center 取验证码 → 登录 → 拿到 Bearer 令牌，全链路可验证。
6. **附带基础防护**：同一账号连续登录失败达到阈值后短暂锁定（返回 `ACCOUNT_LOCKED` / `RATE_LIMITED`），降低在线猜解速率。

## 约束条件（Constraints）

- **不引入第三方验证码服务**：验证码图片自绘（SVG），不引入外部 SaaS、不引入图形处理 crate。
- **不做用户持久化**：账号由环境变量注入（`RTS_AUTH_USERS`），启动时做加盐哈希后驻留内存；**任何口令都不写进代码或文档**，口令哈希不落盘。
- **不内置固定密钥**：`RTS_JWT_SECRET` 未配置时由服务在启动时随机生成，不在代码里留默认密钥。
- **验证码状态存单进程内存**：多实例部署时验证码不跨实例共享，需后续替换为共享存储；本次不引入 Redis 等外部依赖。
- **不做的范围**：滑块/行为验证、短信/邮件 OTP、图形验证码识别模型、验证码音频、跨实例共享存储、完整的用户管理后台。
- **兼容既有前端契约**：令牌形态、错误码命名、`AuthApi` 接口风格保持一致；新增错误码只做增量扩展。
- **安全底线**：验证码答案不通过响应体回传；服务端日志不得记录验证码明文与用户口令。

## 未解决的问题（Open questions）

- 生产环境的 JWT 签名密钥与初始账号来源（配置文件 / 环境变量 / 运维下发）由运维侧确定，本次提供默认开发值并允许环境变量覆盖。
- 多实例部署下验证码共享存储的选型（Redis / 粘性会话）留待架构评审。
- 登录失败锁定的阈值与时长本次取默认值（5 次 / 60 秒），后续按线上情况调整。
