# 需求规格说明书（Spec）: rts-core 基于 tracing 的滚动归档日志模块

依据：`intent.md`（Finalize，含发起人答复）。状态：Finalize |

## 1. 范围

在 `base/rts-core` 中把现有的 `ftail` 日志封装替换为基于 `tracing` 的日志模块，新增：

- 文件落盘（当前仅有控制台输出）；
- **按天 + 按大小**双维度滚动；
- 滚动文件 **GZ 压缩归档**到 `archive/` 子目录；
- 归档文件**默认保留 7 天**，过期自动清理；
- 单文件上限**默认 300 MiB**；
- 同一天内归档**序号从 0 开始**连续递增，跨天归零；
- 保留 `log` facade 兼容桥接，调用方既有用法无需改动。

不在本次范围：日志远程采集/上报、JSON 结构化落盘、日志脱敏/采样/限流、多进程写同一文件的协调、把日志配置并入全局配置体系（`config/configure.rs` 目前是空壳）、rts-center 与 f_matcher 的业务改动。

## 2. 目录与文件布局

### 2.1 日志目录布局

```text
<log_dir>/
├── app.log                      # 当前活动文件（正在写入）
└── archive/
    ├── app.log.2026-10-23.0.gz  # 当天第 1 个归档（序号 0）
    ├── app.log.2026-10-23.1.gz  # 当天第 2 个归档（序号 1）
    └── app.log.2026-10-22.0.gz  # 前一天，序号重新从 0 开始
```

命名规则：`<活动文件名>.<YYYY-MM-DD>.<序号>.gz`。

- 活动文件名默认 `app.log`，可配置；扩展名 `.log` 与 gzip 后缀 `.gz` 同时出现。
- 日期为**该归档内日志内容所属的自然日**（本地时区），不是滚动发生的时刻。
- 序号为**该日期内的归档序号**，从 0 开始连续递增，跨日归零。

### 2.2 模块结构

| 文件 | 职责 |
|----|----|
| `base/rts-core/src/logger.rs` | 模块入口，声明 `config` / `writer` / `log` 三个子模块，导出公共 API |
| `base/rts-core/src/logger/config.rs` | `LogConfig`：目录、文件名、归档目录名、大小上限、保留天数、级别、控制台开关；含默认值与构建器 |
| `base/rts-core/src/logger/writer.rs` | 滚动写入器：按天/按大小判定滚动、GZ 归档、归档序号分配、过期清理；实现 `MakeWriter` |
| `base/rts-core/src/logger/log.rs` | 对外初始化入口 `init()`；级别解析（`RTS_LOG_LEVEL`）；装配 `tracing_subscriber`；本地时间格式化器 |
| `base/rts-core/examples/log_demo.rs` | 演示程序：写入若干条日志，观察滚动与 GZ 归档（人工验证用） |

工作区 `Cargo.toml` 的 `[workspace.dependencies]` 统一声明：`tracing`、`tracing-subscriber`、`tracing-appender`、`tracing-log`、`flate2`、`chrono`、`log`。

`base/rts-core/Cargo.toml` 移除 `ftail`；**保留 `log` 作为直接依赖**（facade 桥接需要用它做 `LevelFilter` 换算与设置 `log` 侧的最大级别）；新增 `tracing` / `tracing-subscriber` / `tracing-appender` / `tracing-log` / `flate2` / `chrono`。

## 3. 配置项

| 配置项 | 默认值 | 环境变量 | 说明 |
|----|-------|---------|------|
| `dir` | `./logs` | `RTS_LOG_DIR` | 日志根目录，不存在时自动创建 |
| `file_name` | `app.log` | — | 活动文件名 |
| `archive_dir` | `archive` | — | 归档子目录名（相对 `dir`） |
| `max_size` | `300 MiB` = `314572800` 字节 | `RTS_LOG_MAX_SIZE` | 单个活动文件的大小上限 |
| `max_age_days` | `7` | `RTS_LOG_MAX_AGE_DAYS` | 归档文件保留天数 |
| `level` | `INFO` | `RTS_LOG_LEVEL` | 日志级别（`off`/`error`/`warn`/`info`/`debug`/`trace`） |
| `console` | `true` | `RTS_LOG_CONSOLE` | 是否同时输出到标准错误 |

- 全部配置项都有可用默认值，调用方零配置即可 `init()`。
- **`LogConfig` 的每个字段用 `Option<T>` 承载**，`None` 表示"调用方未显式设置"。
- **优先级：显式配置 > 环境变量 > 默认值**。
  - 显式传入 `Some(v)` 的字段，直接生效，环境变量不能覆盖（避免静默覆盖调用方的显式意图）。
  - 未显式设置（`None`）的字段，依次尝试环境变量 → 内置默认值。
  - 环境变量取值非法（如 `RTS_LOG_MAX_SIZE=abc`）时回退默认值，并记录一条告警，不导致启动失败。
- `LogConfig::default()` 各字段均为 `None`（即"全部走默认/环境变量"）；配套提供构建器方法（`dir()` / `file_name()` / `max_size()` / `max_age_days()` / `level()` / `console()`）用于显式设置。

## 4. 滚动规则

活动文件在满足**任一**条件时滚动（先判后写，写入前判定）：

1. **跨天**：当前时间已进入新的自然日（本地时区），活动文件属于昨天；
2. **超限**：本次写入前，活动文件已有大小 + 本次写入字节数 > `max_size`。

滚动动作序列：

1. flush 当前活动文件；
2. 把活动文件 `rename` 到 `<archive_dir>/<file_name>.<文件所属日期>.<序号>`——
   rename 只是改目录项，不额外占磁盘空间，磁盘写满时也能成功；
3. 把刚 rename 过去的文件压缩成同名的 `.gz`，压缩成功后删除未压缩的中间文件；
4. 打开新的活动文件（`app.log`，空文件，新建）；
5. 计数器按 §4.1 规则推进；
6. 触发一次过期归档清理（§6）。

### 4.1 序号分配

- 序号按**日期**维度分配：该日期已用序号的最大值 + 1。
- 同一天内连续滚动 → 序号 0、1、2……连续递增。
- 日期变化 → 新日期从 0 重新开始。
- **进程重启后不重置**：启动时扫描 `archive/` 中属于当天的归档文件，取最大序号 + 1 作为起始序号，避免覆盖既有归档。
- 扫描只在**启动时**和**跨天时**各做一次；同一天内的序号在内存里递增，避免每次滚动都全量扫描归档目录。

### 4.2 跨天与重启

- 活动文件携带的"内容所属日期"由**打开该文件时的自然日**决定。
- 进程启动时若已存在 `app.log`：
  - 以其**最后修改时间（mtime）**判定它属于哪一天；
  - 若 mtime 日期 == 今天 → **追加**到该文件（不产生新归档），并按 §4.1 计算当天起始序号；
  - 若 mtime 日期 < 今天（进程上次未正常跨天滚动就退出了）→ 先按 §4 的归档动作把它 GZ 归档到 `archive/`（日期取 mtime 日期，序号取该日期的下一个可用值），再新建今天的 `app.log`。
- 日期判定不需要每写一条日志都取一次时钟：写入器缓存当前日期，并以 **1 秒**为界定期刷新，刷新后才可能触发跨天滚动。

### 4.3 超限判定的边界

判定基于"写入前"的文件大小，因此活动文件大小可能略微超过 `max_size`：

- 若单条日志本身大于 `max_size`，该条日志会完整写入（**不截断日志内容**），此时文件大小超出上限；该条写完后立即滚动。
- 正常情况下活动文件大小不会超过 `max_size`。

## 5. GZ 压缩归档

- 压缩算法 gzip（`flate2`），默认压缩级别。
- 归档文件扩展名 `.gz`，内容为标准 gzip 格式，可被系统 `gunzip` / `zcat` 直接解压还原为原始日志文本。
- 压缩在滚动时**同步完成**（发生在异步写入的工作线程上，不阻塞业务线程）。
- **先落地再压缩**：活动文件先 `rename` 进归档目录，再压缩。这样即使压缩失败，日志内容仍然完整地留在归档目录里，只是没有 `.gz` 后缀；压缩失败时打印告警、保留该未压缩归档，**不丢日志**。
- 压缩失败产生的半成品 `.gz` 会被删除；未压缩的中间文件在压缩成功后删除。
- 归档文件名的日期取**该文件内容所属的自然日**，不是滚动发生的时刻。

## 6. 保留策略与清理

- 保留期默认 **7 天**（`max_age_days`）。
- 判定依据：归档文件名中的日期。归档日期 **>= 今天 - (N-1) 天** 的保留，更早的删除。
  - 例：`N = 7`，今天 `2026-10-23` → 保留 `2026-10-17` ~ `2026-10-23` 共 7 天的归档，删除 `2026-10-16` 及更早的。
- **当天的活动文件 `app.log` 永不因保留策略被删除**。
- 清理时机：**进程启动时**执行一次 + **每次滚动后**执行一次。不做独立的后台定时任务。
- 清理范围仅限 `<log_dir>/<archive_dir>/` 下的归档文件；**不递归、不触碰其它目录、不删除无法解析出日期的文件**（无法解析的文件原样保留，静默跳过——每次滚动都会扫一遍目录，重复告警太吵）。
- 清理失败（权限不足等）只记录错误，不影响业务主流程。

## 7. 初始化与运行期行为

### 7.1 初始化 `init()`

```rust
// base/rts-core/src/logger/log.rs
pub fn init(config: LogConfig) -> Result<LoggerGuard, LoggerError>;
```

初始化顺序：

1. 解析配置（应用环境变量覆盖）；
2. 创建日志目录与 `archive/` 子目录（不存在则创建；失败 → 返回 `Err`）；
3. 执行启动时的过期归档清理；
4. 打开（或按 §4.2 追加/归档）当天的活动文件；
5. 装配 `tracing_subscriber`：
   - 文件层：`fmt::layer()` + 自定义滚动写入器，关闭 ANSI 彩色（文件里要纯文本）；
   - 控制台层：`fmt::layer()` 输出到标准错误（可关闭）；
   - **时间戳用本地时区**（`chrono::Local`，格式 `%Y-%m-%dT%H:%M:%S%.6f%:z`），
     与归档文件名里的本地日期对得上；默认的 UTC 时间戳在跨时区排查时容易错位；
   - 全局级别过滤器：由配置级别确定，`off` 相当于完全静默；
6. 注册 `log` facade 桥接（`tracing-log`），使既有 `log::info!` 等宏的输出进入同一份日志文件与控制台；
7. 返回 `LoggerGuard`。

### 7.2 `LoggerGuard`

- 因采用**异步非阻塞**写入，必须持有 guard 才能保证进程运行期间日志工作线程存活；guard 被 drop 时，工作线程会 flush 缓冲区并退出。
- 因此 `init()` 返回 `LoggerGuard`，调用方需持有它（例如 `let _guard = init(cfg)?;`）。`r_connector` 按此改造。

### 7.3 异步非阻塞写入

- 使用 `tracing_appender::non_blocking` 的非阻塞写入器包裹滚动写入器。
- **滚动、GZ 压缩、过期清理全部发生在工作线程上**（非阻塞写入器的工作线程内执行实际写入），因此压缩这类耗时操作不会阻塞业务线程。
- 缓冲行为：采用**有界通道 + 丢弃最旧**的策略以避免内存无限增长（`lossy` 语义）；日志量超过消费能力时，最旧的待写日志被丢弃——需在实现中记录一次告警。**具体参数（通道容量、是否 lossy）见 §9 Q2**。
- 进程被 `kill -9` 时，缓冲区中尚未落盘的日志会丢失。这是选择异步非阻塞的已知代价。

### 7.4 错误处理原则

| 场景 | 行为 |
|----|----|
| 日志目录创建失败 | `init()` 返回 `Err`，由调用方决定是否终止进程 |
| 活动文件打开失败 | `init()` 返回 `Err` |
| 滚动时 GZ 压缩失败 | 保留原活动文件、记录错误日志、继续使用同一文件（不丢日志） |
| 清理过期归档失败 | 记录错误日志，不影响其它流程 |
| 写入失败（磁盘满等） | 记录错误到标准错误，不 panic；后续写入继续尝试 |

日志模块自身的错误一律**不 panic**，不中断业务主流程（除 `init()` 阶段的致命错误外）。

## 8. 对现有调用方的影响

| 调用方 | 现状 | 改造后 |
|----|-----|------|
| `toolkit/r_connector/src/main.rs` | `rts_core::logger::log::init(LevelFilter::Warn)`，日志宏用 `log::info!` | `rts_core::logger::log::init(LogConfig::default().level(LevelFilter::WARN))`；**日志宏保持 `log::info!` 不变**（兼容桥接生效），仅级别类型改为从 rts-core 取 `LevelFilter`（`tracing` 的 `LevelFilter`，含 `OFF`） |
| 其它模块 | 无 | 无 |

`log` facade 的 `LevelFilter` 与 `tracing` 的 `LevelFilter` 取值一一对应，转换关系在 rts-core 内提供（`level_to_log` 私有函数 + `level_from_log` 公开函数）。

**注意**：`r_connector` 的 `main` 用 `std::process::exit` 结束进程，而 `process::exit` **不执行析构**——异步写入的 `LoggerGuard` 若随 `run()` 返回被析构，缓冲就来不及 flush。因此 `run()` 拆成 `run()`（持有 guard）+ `run_inner()`（原业务逻辑），在 `run_inner` 返回后显式 `drop(guard)` 再返回退出码。

## 10. 验证方式

1. `cargo build --workspace` 通过；`cargo test --workspace` 通过。
2. **单元测试**（`logger::writer`）：
   - 写满触发滚动，生成序号 0、1、2…… 的归档；
   - 跨天后序号归零为 0；
   - 归档文件是合法 gzip，`gunzip` 后内容与原始写入一致；
   - 超过保留期的归档被删除、当天归档与活动文件存活；
   - 归档目录中无法解析日期的文件不被删除。
3. **集成测试**（`base/rts-core/tests/logger.rs`）：
   - 以 `max_size = 1 KiB` 初始化，写入超过阈值的日志，核对 `archive/` 下出现 `app.log.<今天>.0.gz`、`.1.gz`… 且序号连续；
   - 验证 `log::info!`（facade）与 `tracing::info!` 都落到文件中；
   - 验证启动时的过期清理删除了构造出来的过期归档。
4. **手工验证**：以默认 300 MiB 配置启动 `r_connector`，确认生成 `logs/app.log`；用 `max_size` 调小（如 1 MiB）验证滚动与 GZ；`zcat` 归档文件确认内容完整。
5. `cargo clippy --workspace --all-targets` 无告警。

## 11. 不做（重申）

- 不做日志远程采集/上报，不接 Loki / ES / OTLP。
- 不做 JSON 结构化日志输出（本次保持人类可读文本格式）。
- 不做日志脱敏、采样、限流。
- 不做多进程 / 多线程写同一文件的协调。
- 不做独立的后台定时清理任务（清理只发生在启动与滚动时刻）。
- 不把日志配置并入 `config/configure.rs` 的全局配置体系。
- 不改动 rts-center、f_matcher 的业务逻辑。
