# 意图（Intent）: rts-core 基于 tracing 的滚动归档日志模块

Author: zhtao. 状态：Finalize |

## 问题（Problem）

`base/rts-core` 目前只有一个极简日志封装 `src/logger/log.rs`：基于 `ftail` 走 `log` facade，仅向**控制台**输出，级别由环境变量 `RTS_LOG_LEVEL` 覆盖。项目是多模块工作区（`rts-core` / `rts-center` / `r_connector` / `f_matcher`），落地到真实服务器上有四个问题：

1. **日志无处落盘**：进程输出只进 stdout，在容器化 / systemd 采集场景下会被丢弃；rts 平台的核心职责是任务（receive → transform → sink）调度与监控，任务在哪个环节失败、失败时携带了哪些上下文，事后无从追查。
2. **磁盘占用不可控**：没有滚动与清理策略，一次异常刷屏或长期运行就能把日志盘写满；日志与业务数据同盘时，会直接拖垮 sink 落盘。
3. **归档无压缩**：纯文本日志 gzip 压缩比通常在 5~10 倍。默认 300M 粒度的单文件，在"保留一周"的策略下会累积到数 GB，占用本可用于业务数据的空间。
4. **技术栈与平台规划不匹配**：现有实现基于 `ftail`（`log` facade 家族），拿不到 `tracing` 的 span / 结构化字段能力；而"任务调度监控"后续要做链路追踪（一次任务从 receive 到 sink 的上下文贯穿），`tracing` 是这条路线的地基。

需要一个**可复用的日志模块**放在 `rts-core` 里：基于 `tracing` 封装，文件落盘，**按天 + 按大小**双维度滚动，滚动下来的文件**用 GZ 压缩归档**，归档文件**默认保留一周**，单文件大小**默认 300M**，同一天内的归档**序号从 0 开始递增**。

## 预期结果（Proposed outcome）

**可度量的完成标识：**

1. `base/rts-core` 新增日志模块，公共 API 位于 `rts_core::logger`，对外暴露"配置 + 初始化"两个动作即可完成落盘，无需调用方自己拼 `tracing_subscriber`。
2. **滚动行为**：
   - **按天**：跨自然日（本地时区）自动切换到新文件。
   - **按大小**：单个日志文件写满阈值（默认 300M）即滚动，滚动前触发的大小以"写入前判断"为准，不允许单个文件超过阈值。
   - **双条件并存**：先满足者触发滚动（跨天 or 超限）。
3. **归档命名**：同一天内的归档文件**序号从 0 开始**连续递增（当天第一个归档为 0，第二个为 1……）；跨天后序号**重新从 0 开始**。命名可被脚本解析（日期与序号可分离）。
4. **GZ 压缩归档**：滚动产生的历史文件以 **gzip** 格式落盘（`.gz` 后缀），内容可被标准 `gunzip` 解压还原；压缩在滚动发生时同步完成，落盘前原文件不残留。
5. **保留策略**：归档文件**默认保留 7 天**，超过保留期的归档文件被清理；当天正在写的活动文件永不被清理。保留天数可配置。
6. **默认参数**：单文件上限 **300M**，保留期 **7 天**，日志目录与文件名可配置；日志级别沿用现有约定（环境变量 `RTS_LOG_LEVEL` 覆盖）。
7. **生命周期**：进程启动时完成"建目录 → 清理过期归档 → 打开当日活动文件"；滚动与清理的失败**不影响业务主流程**（降级为告警，不 panic、不中断）。
8. **可观测性**：滚动、归档、清理等关键动作本身有迹可循（写入日志/标准错误），便于运维确认"到底是哪次滚动把文件切了"。

**验证方式（本地可自测）：**

- 单元测试：滚动触发条件（跨天 / 超限）、归档序号从 0 递增且跨天归零、GZ 内容可解压还原、过期归档被删除且活动文件存活。
- 集成测试：以极小阈值（如 1KB）启动日志模块，写入超出阈值的日志，核对目录中出现 `序号 0,1,2...` 的归档文件且为合法 gzip。
- 回归：`cargo build --workspace` 与 `cargo test --workspace` 通过。

## 约束条件（Constraints）

**技术约束**

- 遵循仓库既有规约：走 `立项 → 开发 → 验证 → 交付 → 发布` 流程，产出物落在 `sdlc/20261023_rts-core日志模块/`；所有开发在独立 worktree（`.claude/worktrees/feature-logger/`）中进行，本机验证通过后提交分支并提 PR；主仓只用于拉取与只读查看。
- 依赖取用本地已缓存的版本（`tracing 0.1.44` / `tracing-subscriber 0.3.23` / `flate2 1.1.x` / `chrono 0.4.45`），构建可离线进行。
- 滚动写入器需自行实现：`tracing-appender` 只提供按时间的滚动（hourly/daily），**不提供按大小滚动**，且归档压缩与保留策略均无内置支持。

**明确不做（本次范围外）**

- 不做日志的远程采集 / 上报（不接 Loki、ES、OTLP 等）。
- 不做结构化日志落盘（JSON 格式）——本次保持人类可读的文本格式。
- 不做日志内容脱敏、采样、限流。
- 不做多进程 / 多线程写入同一文件的协调（同一进程内多线程共享一个写入器，写入串行化由模块内部保证）。
- 不改动 rts-center、f_matcher 的业务逻辑。

## 已解决的问题（Resolved questions）

1. **归档文件命名格式**（已确认）：`app.log.2026-10-23.0.gz`，归档统一放在日志目录下的 `archive/` 子目录。
2. **"300M" 的口径**（已确认）：**300 MiB**（`314572800` 字节），按 1024 进制。
3. **现有 `log::` facade 调用如何处理**（已确认）：**保留兼容桥接**——安装 `tracing-log` 的 `LogTracer`，`r_connector` 的 `log::info!` 等宏调用不改动，同样写入日志文件。
4. **写入方式**（已确认）：**异步非阻塞**（`tracing-appender` 的 `non_blocking`），有界通道 + 丢弃最旧。
5. **配置优先级**（已确认）：显式 `LogConfig` > 环境变量 > 内置默认值。
6. **控制台输出**（已确认）：默认保留（stderr + 文件双输出），可配置关闭。
7. **环境变量覆盖范围**（已确认）：`RTS_LOG_LEVEL` / `RTS_LOG_DIR` / `RTS_LOG_MAX_SIZE` / `RTS_LOG_MAX_AGE_DAYS` / `RTS_LOG_CONSOLE` 全部提供。
